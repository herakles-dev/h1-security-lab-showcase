# The Decision Rules Engine

A skilled bug bounty hunter doesn't reason from first principles on every request. Most of what separates a seasoned researcher from a scanner is a huge library of compiled micro-decisions, the kind that fire almost unconsciously: *see a JWT, check the algorithm. See CORS reflecting an arbitrary origin, check whether auth rides on a cookie. See sequential integer IDs, make IDOR the first thing you try, not the fifth.* None of that is deep reasoning in the moment — it's pattern recognition built up over hundreds of targets, and it's exactly the kind of knowledge that normally lives only in one person's head, degrades when they're tired, and resets to zero when somebody new starts. A gut instinct you can't grep is a gut instinct with a bus factor of one.

This system takes that tacit knowledge and makes it explicit. The result is a single table — the Decision Rules table — that maps observed situations to prescribed actions, embedded directly in the project's core instruction file. It's not a nice-to-have reference; it's load-bearing doctrine that the AI consults mid-hunt, the same way a human researcher's gut would.

## How It Works

The table has two columns: **Situation** and **Action**. A situation is something the hunt produces — a response header, a token format, a tool's output, an architectural fact about the target. An action is a specific next step, usually naming the exact tool and flag to run.

During a hunt, the AI isn't following a rigid linear script. It's exploring a target, running tools, reading responses. At each point where something in the table matches what it just observed, the table's prescribed action takes priority over whatever the AI might have improvised on its own. If a response includes a JWT, the rule fires immediately rather than depending on the AI remembering to check it that particular day. If two accounts have just been created, the rule reorders priorities so the IDOR test with `--compare-field` jumps ahead of lower-value probes.

This is the core distinction between a tool-calling AI and a tool-calling AI with doctrine: the first improvises every time; the second has already pre-committed to its best-known response for dozens of recurring situations, and only improvises where the table is genuinely silent.

## Categories of Rules

The table has grown past forty rows. They cluster into a handful of natural categories.

**Discovery triggers** fire the moment a particular artifact or technology shows up. Found a JWT — decode it immediately and check algorithm, key ID, and JKU, because `alg: none` or a weak key confusion is often sitting right there in plaintext. Found a GraphQL endpoint — try introspection before anything else, because an exposed schema turns every subsequent guess into certainty. Fingerprinted the tech stack — pull the framework-specific attack playbook instead of running generic wordlists against a target whose weaknesses are already well cataloged by version and vendor.

**Authentication and access** rules route effort toward or away from entire attack classes depending on how the target is built. Multiple accounts available means the differential IDOR test is the single highest-priority action, full stop — nothing else on the board has a better ratio of effort to expected finding. But the *same* signal, cookie-based auth versus header-based auth, flips the priority of a totally different class: cookie auth makes CORS testing a potential account-takeover vector worth real attention, while header-based JWT auth makes that same CORS test low-value, because there's no ambient credential for a malicious origin to ride on.

**Transport and infrastructure** rules exist because the surface layer lies. A 403 on an interesting endpoint isn't a dead end — it's an instruction to run a 403-bypass pass before accepting the wall as real. A proxy-fronted target gets tested for HTTP request smuggling, because the proxy boundary itself is often the vulnerable seam. And — a rule that only exists because it was learned the hard way — a uniform wall of 403s or 401s across an entire sweep is treated as a transport-layer block (a CDN or WAF fingerprinting the scanner itself), not as evidence the application is secure. Banking a transport artifact as "tested, secure" was a real failure mode until the rule made the distinction explicit. The system called a target "secure" because the CDN was politely refusing to speak to it.

**Coverage and completeness** rules guard against false signal from noisy tooling. A burst-mode scanner hit against a CDN-fronted target is a candidate, not a confirmed finding — concurrent request bursts against rate-limited infrastructure produce transient phantom hits, so every one gets re-verified with a single sequential request before it's trusted. Output from crawling tools like historical-URL archives gets filtered through a status-code/content-type check first, because raw crawler output conflates "this URL was once requested" with "this URL was ever a real, served file" — treating the former as the latter floods secret-scanning with noise.

**Reporting and judgment** rules sit closest to the business end of the process, where the cost of a mistake is reputational, not just wasted time. A low-severity finding triggers an escalation check — can it be chained into something higher-impact before it's written up as-is? Before any finding is written at all, the devil's-advocate rule fires: write the target's dismissal of the bug first, in their voice, then disprove it with evidence. If the dismissal can't be disprovable, the finding doesn't get submitted. And underneath all of it sits the simplest gut-check rule in the table: *would I pay a bounty for this?* If the honest answer is no, it doesn't go out, because weak submissions cost reputation on every future report from the same account. Reputation is the only currency that compounds in both directions.

**Mobile-specific** rules handle a lane with its own physics. An in-scope mobile app defaults to testing on a genuine physical device rather than an emulator, because modern integrity checks (hardware attestation, root detection) treat emulated and rooted environments as untrusted and simply refuse to run. An app that's both TLS-pinned and attested can't be intercepted with a traditional proxy-in-the-middle setup at all — the rule routes around that wall entirely, capturing the auth token through a real browser session on the device instead of fighting the pinning. And when static analysis fingerprints the app's auth provider as a well-known identity platform (the kind of managed login service many apps delegate to rather than rolling their own), a rule catches a subtlety that's easy to miss: the vendor's own login code is out of scope, but the *program's own configuration* of that service — which account attributes can be changed, whether self-registration is open, how redirects are allow-listed — is squarely in scope and is routinely under-tested, because it looks like someone else's infrastructure until you look closely.

## How the Table Grows

No rule in the table was invented speculatively. Every row traces back to a real hunt where either the system made a wrong call, or a human operator caught something the system had missed, or a tool got built that changed what the right next action even was. The table didn't start at forty rows — it started much smaller, and it grew exactly once per lesson, never more.

That provenance matters more than the current row count. A rule that says "treat a uniform 403/401 sweep as a transport block, not a secure result" exists because, at some point, the opposite mistake actually happened — a wall of identical denials got banked as "endpoint secure" when it was really a CDN silently fingerprinting and blocking the scanning traffic itself. Writing the rule down means that specific mistake has a maximum lifetime of one occurrence. The next hunt — on a different target, run by a different session with no memory of the first one — inherits the fix automatically, because the fix lives in the table, not in anyone's recollection of how the mistake happened.

This is also why the table lives in the project's core instructions rather than in a wiki page or a training document somewhere else. Instructions that live beside the tools get read every single time; a lesson filed away in a retrospective doc gets read once, by the person who wrote it, and then quietly stops mattering.

## Rules vs. Judgment

None of this makes the table a replacement for reasoning. It's doctrine, not law — the AI can and does deviate when the context genuinely calls for it, and the table doesn't attempt to cover every situation a hunt could produce. What it guarantees is narrower and more important: for the situations that recur across hunts, the known-good response fires every time, without depending on anyone remembering to apply it that day.

The alternative — "just use good judgment each time" — sounds reasonable until you notice what it actually produces in practice: the same category of mistake recurring across different sessions, each one rediscovering a lesson some earlier session already paid for. A rule table converts a lesson into an asset. Judgment stays exactly where it belongs — at the edges, on genuinely novel situations the table hasn't seen yet — while everything the table has already seen gets handled the same correct way, every time.
